## 1. Goal

The app is live on one HTTPS origin, Bunty takes real orders with it, and the brief §30 definition of done is verified **in production on his phone**. Also in place: the operational basics a real business needs (backups with a tested restore, uptime alerts, a rollback procedure, an incident playbook) and a one-page guide for the vendor.

Phase 1 is complete only when Bunty has run a real day of orders through it.

## 2. Scope

**In:** platform choice and `render.yaml`; managed Postgres; production env vars; build / pre-deploy / start commands; health check; initial data and admin creation; smoke test; production verification with the vendor; optional custom domain with a canonical-host redirect; monitoring; backups and a restore drill; deploy and rollback rules; incident playbook; launch materials; vendor guide; first-week watch list.

**Out:** staging environment, CDN, autoscaling, log drains, error-tracking services (all fine for Phase 2 if needed).

## 3. Platform

**Render** is the default (brief §23 lists it first; owner question Q5). Railway works the same way (§4.3).

| Requirement | Why |
|---|---|
| **Paid** web instance (smallest "starter" tier) | Free web services sleep when idle; the first customer after a quiet hour waits 30–60 s and gives up. |
| **Paid** Postgres (smallest tier) | Free databases expire and have no backups. Paid plans include daily backups. |
| **Singapore** region for both | Closest region to India; web and DB in the same region keep queries fast and on the private network. |
| One web instance | Batch 1 §3.3: in-memory rate limits assume one instance. |

Check current plan names and prices at setup time; the owner confirms the monthly cost before anything is created.

## 4. Configuration

### 4.1 `render.yaml` (committed)

```yaml
services:
  - type: web
    name: bbc-web
    runtime: node
    region: singapore
    plan: starter                      # verify current name
    branch: main
    autoDeploy: true
    buildCommand: corepack enable && pnpm install --frozen-lockfile --prod=false && pnpm build
    preDeployCommand: pnpm db:deploy   # prisma migrate deploy, before traffic switches
    startCommand: pnpm start
    healthCheckPath: /api/health
    envVars:
      - key: NODE_ENV
        value: production
      - key: NODE_VERSION
        value: "24"
      - key: DATABASE_URL
        fromDatabase:
          name: bbc-db
          property: connectionString   # internal URL (private network)
      - key: JWT_SECRET
        generateValue: true
      - key: APP_ORIGIN
        sync: false                    # set by hand: https://bbc-web.onrender.com, later the custom domain

databases:
  - name: bbc-db
    region: singapore
    plan: basic-256mb                  # smallest paid plan; verify current name
    postgresMajorVersion: "16"
```

Notes:

- `--prod=false` matters: with `NODE_ENV=production` set, `pnpm install` would skip devDependencies (Vite, TypeScript, Prisma CLI) and the build would fail (Batch 2 §11).
- `preDeployCommand` runs migrations once per deploy, before the new version receives traffic. If it fails, the deploy stops and the old version keeps serving.
- If boot-time config validation fails (Batch 1 §11), the health check never passes and Render keeps the previous version live.
- Keep Prisma's connection pool small (≤ 10 connections); the smallest Postgres plans have low connection limits.

### 4.2 Production environment

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | Render internal connection string (from the database) |
| `JWT_SECRET` | generated by Render (≥ 32 chars); never copied anywhere else |
| `APP_ORIGIN` | `https://bbc-web.onrender.com` → the custom domain later |
| `TRUST_PROXY` | unset (defaults to 1 in production) |

## 5. Optional: canonical host

When a custom domain is added (Q6), the `onrender.com` URL keeps working. Admin writes from it would fail the Origin check, and two URLs confuse people. Add `src/server/middleware/canonical-host.ts`:

- production only;
- for `GET`/`HEAD` requests to non-`/api` paths whose `req.hostname` ≠ the hostname of `APP_ORIGIN` → `301` to `APP_ORIGIN` + original path and query;
- `/api/*` is never redirected, so a customer who loaded the page on the old host can still place their order and the platform health check keeps working;
- covered by an integration test with a forged `Host` header.

## 7. Smoke test (after every deploy that changes behaviour; ~10 minutes)

1. `curl -i https://<host>/api/health` → `200 {"status":"ok"}`.
2. `curl -sI https://<host>/` → `Strict-Transport-Security`, `Content-Security-Policy`, no `X-Powered-By`, `Cache-Control: no-cache`.
3. `curl -sI https://<host>/assets/<entry>.js` → `immutable`; note `content-encoding` (Batch 7 §6.3 compression decision).
4. `curl -sI https://<host>/api/menu` → `Cache-Control: no-store`.
5. `http://` redirects to `https://` (platform).
6. On a phone over mobile data: menu loads; place an order named "TEST – ignore"; confirmation shows the order ID; lookup works; wrong phone fails.
7. Admin on a phone: log in; the test order appears in its batch group; cancel it; the stock returns.
8. Browser devtools: `bbc_admin` cookie is `Secure`, `HttpOnly`, `SameSite=Lax`.
9. Render logs: request lines show method, path, status and duration; no phone numbers, no bodies.

Test orders stay in the history (nothing is ever deleted); they are cancelled and clearly named.

## 9. Custom domain (optional, Q6)

1. Buy the domain; in Render add it to `bbc-web`; create the DNS records Render shows (CNAME for a subdomain such as `order.<domain>`); TLS is issued automatically.
2. Set `APP_ORIGIN=https://order.<domain>`; redeploy; enable the canonical-host redirect (§5).
3. Admin login again on the new domain (cookies are per host).
4. Update the QR code, WhatsApp message and Open Graph URL.

## 10. Operations

### 10.1 Monitoring

- Render health checks restart an unhealthy instance automatically.
- External uptime monitor (e.g. UptimeRobot's free tier) on `/api/health` every 5 minutes, alerting the developer by email (and Bunty by SMS if the owner wants).
- Logs: Render log stream. Every `500` carries a `requestId` (also returned to the client in `details.requestId`), so a customer's screenshot leads straight to the log line.
- Render's dashboard shows CPU, memory and response times; check it during the first week's evening peaks.

### 10.2 Backups

- Paid Render Postgres takes daily backups automatically; confirm the retention period on the chosen plan and write it in `docs/runbook.md`.
- **Before every deploy that includes a migration:** take a manual backup (`pg_dump --format=custom "$EXTERNAL_DATABASE_URL" -f bbc-YYYY-MM-DD.dump`).
- Weekly manual dump stored in an encrypted, private location (it contains customer names and phone numbers).
- **Restore drill** before launch: `pg_restore` the latest dump into a local database, point `start:local` at it and open the dashboard. Record the date in the runbook. A backup that has never been restored doesn't count.

### 10.3 Deploys and rollback

- Deploy from `main` only, after CI is green. Avoid deploying between 6:30 and 9:30 PM IST (batch rush).
- Render deploys without downtime: the old instance serves until the new one passes its health check. The in-memory rate-limit counters reset on deploy (acceptable).
- Migrations follow expand/contract (Batch 1 §7.3), so the previous app version keeps working after a migration. That makes **Rollback** in Render (redeploy the previous build) safe without touching the database.
- A bad migration is fixed forward with a new migration. Restoring a backup is only for data loss, and it loses every order since the backup, so it's the owner's call.

### 10.4 Secrets

- Rotating `JWT_SECRET` (Render env var → redeploy) logs the vendor out; nothing else is affected.
- Database credentials are rotated in Render; `DATABASE_URL` updates automatically through `fromDatabase`.
- Nobody copies production secrets into chat, email or local files beyond the temporary external-URL use in §6 and §10.2.

## 11. Incident playbook

| Symptom | First actions |
|---|---|
| Uptime alert / site down | Render status page and logs → restart the service → roll back the last deploy if it started after it |
| Customers report errors placing orders | Logs by `requestId`; if widespread, Bunty pauses orders from the admin (customers see the paused message instead of errors); roll back |
| Suspected wrong stock or overselling | Run the inventory invariant query (Batch 1 §7.5) with `psql`; correct today's stock from the Stock screen; report the rows for a bug fix |
| Prank-order flood | Pause all; cancel the fake orders; check whether the per-phone cap and IP limits held; tighten `src/shared/limits.ts` if needed and redeploy |
| Vendor locked out or phone lost | Render Shell → `pnpm admin:reset-password:prod` (also logs out every device) |
| Database full or slow | Render metrics; upgrade the plan (no code change) |

## 14. Vendor guide (`docs/vendor-guide.md`)

One printed page in plain language (Hindi version if the owner wants), with screenshots:

1. Every morning: Stock → Use yesterday's numbers → change what's different → Save.
2. During the day: keep **Today** open. New orders say NEW and make a sound.
3. Batch: at cutoff, the card shows exactly what to pack. After delivering: **Mark all done**.
4. Express: each card shows where and by when. After delivering: **Cash collected**, then **Done**.
5. Out of something? Set its stock, switch Express off, or close a slot for today.
6. Need a break? Switch **Orders** off. Remember to switch it back on.
7. Fake order? Open it → Cancel. The food goes back into stock.
8. Site not working? Switch to WhatsApp for the day and call <developer number>.
